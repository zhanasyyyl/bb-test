# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A Django 5.2 app that recreates the College Board "Bluebook" digital SAT testing app UI in the browser (deployed at `bbtest.shop`). One project (`bluebook_project`) with a single app (`ui`). No frontend build step: all UI is Django templates with inline CSS/JS plus `ui/static/`.

## Commands

```bash
pip install -r requirements.txt
cp .env.example .env              # sets DEBUG=True; add DESMOS_API_KEY by hand for the calculator
python manage.py migrate
python manage.py runserver        # dev server
python manage.py createsuperuser  # needed for /question-editor/ and /admin/
python manage.py test ui          # run tests
python manage.py test ui.tests.SomeTestCase.test_method   # single test
python manage.py deactivate_users # sets is_active=False on every non-staff user
python manage.py skip_test [on|off] # lets students skip modules and breaks by clicking the timer, or shows the state
python manage.py telegram_setup   # points the Telegram bot's webhook at the site (update.sh runs it on deploy)
python manage.py email_telegram_links [--send] # one-off: emails contact addresses their Telegram connect links (dry run without --send)
python manage.py collectstatic    # required in production (nginx serves staticfiles/)
gunicorn bluebook_project.wsgi -c gunicorn.conf.py   # production (binds 127.0.0.1:8000, 9 workers)
```

There is no linter or formatter configured.

`DEBUG` defaults to False when unset, and then `SECRET_KEY` is required, so `manage.py` fails without a `.env`. Run tests with `DEBUG=True`; with `DEBUG=False`, more than half of them fail or error.

`deploy/update.sh` deploys on the server (pull, requirements, migrate, collectstatic, check, Telegram webhook, gunicorn reload, health check). The rest of `deploy/` is server config installed by hand, not applied by deploys: an nginx per-IP rate limit for sign-in POSTs (student and admin), nginx compression and cache headers for `/static/`, and a daily `clearsessions` cron script. See `deploy/README.md`. Production runs behind nginx, which serves `/static/` itself.

## Architecture

**User flow (URL order):** `/` (fake login landing) → `/cb_login/` (real auth via email-as-username) → `/dashboard/` → `/setup/`, `/setup_step2/` … `/setup_step8/` → `/start-code/` → `/test/` → `/congrats/`. Setup step routes are generated in a loop in `ui/urls.py` as `TemplateView`s and have no view logic.

**Users** are created by an admin (no signup). `UserProfile` (one-to-one with `auth.User`) holds `full_name`, `test_center_address`, `start_code`, `test_completed` and the linked Telegram chat (`telegram_chat_id`, `telegram_chat_name`, `telegram_link_token`). `contact_email` is no longer used; it's kept, read-only in admin, so old values aren't lost. `test_completed` swaps the dashboard's registration card for a "no upcoming tests" card, and logging in through `cb_login_view` resets it to False. Failed sign-ins are recorded in `LoginFailure`, and an account is locked once it has 10 failures in a 15-minute window. The lockout lives in the authentication backend (`ui/auth_backends.py`, set in `AUTHENTICATION_BACKENDS`), so it covers both `/cb_login/` and the Django admin login. The limit is per account rather than per IP, because students at a test center share one IP. Sign-out is a POST to `/logout/`. Passwords use PBKDF2 at 200,000 iterations (`ui/hashers.py`) instead of Django's 1,000,000, because sign-in is CPU-bound; it replaces Django's PBKDF2 hasher in `PASSWORD_HASHERS` (same algorithm name, so old hashes still verify and are re-hashed on next sign-in). The profile can be missing, so views fetch it with `_get_profile()` and check for None.

**Questions** are stored in `ui/data/questions.json`, not in the database. Each entry has `id`, `type` (`"rw"` or `"math"`), `question`, an optional `passage`, and optional `options` (math questions without `options` are student-produced response). There is no answer key. Math text uses `$...$` delimiters and is rendered client-side with MathQuill.
- `get_cached_modules_json()` in `ui/views.py` splits the questions by type into the 4 modules defined in `MODULES` (RW 27+27, Math 22+22). It caches the result keyed on the file's mtime, so every gunicorn worker picks up edits. Because the file is sliced by position, order within each type matters, and questions past those counts are ignored. A short bank only logs a warning and produces short modules.
- Question text embeds images as hardcoded `/static/images/...` URLs, not `{% static %}`. Those paths are unhashed and cached for an hour (`WHITENOISE_MAX_AGE`, `deploy/nginx/static-expires.conf`), so replacing an image in place can take that long to show. If the file can't be read, `/test/` returns a 503.
- `/question-editor/` (superuser only) is an in-browser editor that GETs and POSTs the entire JSON array to `/api/questions/`. A POST is checked by `validate_questions()` (structural errors give a 400 and the file is not touched; short counts only return `warnings`), then written atomically with a temp file and `os.replace`.
- `scripts/` holds one-off JSON migration scripts. Run them from the repo root, since they use the relative path `ui/data/questions.json`.
- Tests that touch the file should subclass `QuestionsFileTestCase` in `ui/tests.py`, which points `views.QUESTIONS_FILE` at a temp copy.

**Test interface** (`ui/templates/test_interface.html`, ~3400 lines) is a single-page app in one template. The server injects `modules_json` (parsed with `escapejs`) and `desmos_api_key`. All test state lives in a global JS `app` object plus `moduleState`, in memory only (no `localStorage`). Nothing about answers is sent to the server. The only server calls are `POST /api/mark-test-completed/`, made by `finishTest()` at the end, `POST /api/unscheduled-break/` when an unscheduled break starts or ends (`unscheduled_break_view`; only the module index and timings are sent), and `POST /api/note/` when the student clicks away from a changed note or collapses the notes panel (`note_view`). Both send a Telegram message to the student's linked chat. They go through one queue in the page (`queueNotice()`), which retries notices that failed offline when the connection is back. A note is free text, so it is capped per hour, cut to `NOTE_MAX_CHARS` and HTML-escaped. If the device is offline, `finishTest()` shows a "Reconnect to Finish" message and retries until it gets through, then goes to `/congrats/`. Clicking the module or break timer skips it only when `can_skip` is true: always for staff, and for students when `SiteSettings.allow_skipping` is on (`manage.py skip_test`, off by default). The value is read when `/test/` loads, so open tests keep theirs until reloaded. The More menu's Help, Shortcuts, Assistive Technology, Line Reader and Exit the Exam, plus the keyboard shortcuts (matched on `e.code`, since Option changes `e.key` on a Mac), live in `ui/templates/partials/_test_tools.html`, included at the end of the test page. The shortcuts dialog lists the real app's full table, including rows for features this site doesn't have; those keys do nothing. The Desmos calculator (`ui/static/calculator.js`) is lazy-loaded on first use. MathQuill's stylesheet and Symbola font are served from `ui/static/vendor/mathquill/` (cdnjs fonts are blocked by the CSP); `mathquill.js` and jQuery still come from CDNs, loaded in `base.html` with SRI hashes.

**Templates:** every page extends `base.html` except `question_editor.html`, which is standalone. `base.html` depends on these context values:
- `debug_mode` (from the `ui.context_processors.debug_mode_context` context processor) gates the anti-inspection script, which blocks right-click and the devtools and view-source shortcuts. That script only runs when `DEBUG=False`. Don't detect devtools from window sizes (outer vs inner): browser zoom and side panels trigger it, and it used to blank the page.
- `static_files_preloader` adds `<link rel="prefetch">` for a hand-maintained list of UI images (`_PREFETCH_IMAGES` in `ui/context_processors.py`).

**Messages (Telegram; the only email is the one-off `manage.py email_telegram_links`, which sends each stored contact address its students' connect links through Resend's API directly):** start codes (`start_code_view`, 6-digit codes only), unscheduled breaks and notes are sent by a Telegram bot to the student's one linked chat; with no linked chat nothing is sent. The dashboard profile window shows the student's connect link, `t.me/<TELEGRAM_BOT_USERNAME>?start=<telegram_link_token>` (`telegram.connect_link()`), in a read-only box with a Copy button, for the student to send to their assistant; whoever opens it and presses Start sends `/start <token>` to the bot. Telegram posts that to `telegram_webhook_view` (`/telegram/webhook/`, CSRF-exempt, only accepted with the `X-Telegram-Bot-Api-Secret-Token` header equal to `TELEGRAM_WEBHOOK_SECRET`), which links the chat (replacing any earlier one); `/stop` unlinks it. `/finished` sets `UserProfile.tutor_finished_at` (a chat linked to several students gets a button per student, sent back as a `callback_query`); the congrats page polls `GET /api/tutor-finished/` every 5 s and then turns its lowest confetti piece black. Entering a start code clears it. Replies are returned as the webhook response. `manage.py telegram_setup` registers the webhook. Messages are Telegram HTML rendered from `ui/templates/telegram/*.html` (autoescaped; only Telegram's tags such as `<b>`, `<code>`, `<blockquote>`, and newlines are kept), queued by `enqueue_message()` in `ui/message_queue.py` as `QueuedMessage` rows, and sent with `telegram.send_message()` (stdlib HTTP, no SDK, IPv4 only because the server's IPv6 route to Telegram sometimes hangs for the whole timeout; errors never include the URL because it contains the token). Hourly caps are per `QueuedMessage.category`: `START_CODE_MESSAGES_PER_HOUR`, `UNSCHEDULED_BREAK_MESSAGES_PER_HOUR`, `NOTE_MESSAGES_PER_HOUR`. Sender threads run in every server process: `start_workers()` is called from `bluebook_project/wsgi.py`, so they don't run in management commands or tests, but they do run under `runserver`, which sends real messages if `TELEGRAM_BOT_TOKEN` is valid. They claim rows from the shared table with a conditional UPDATE. Failures retry with backoff (or after Telegram's `retry_after`) and are marked `failed` after 5 attempts; a permanent error (bot blocked, chat gone) fails at once and unlinks that chat. The `QueuedMessage` admin shows their status. Telegram allows ~30 messages/s per bot, so a 25/s budget is split across `MESSAGE_SENDER_PROCESSES` processes, which must match `workers` in `gunicorn.conf.py`. Don't enable gunicorn `preload_app`, or the threads would start before fork and die in the workers. In tests, mock `telegram.send_message` and call `message_queue.process_one()` directly.

**Database:** SQLite in WAL mode with `transaction_mode: IMMEDIATE` and a 20 s busy timeout (see `DATABASES` in settings), so concurrent writes from the gunicorn workers wait instead of failing. The login lockout relies on IMMEDIATE to make its check-and-record atomic (`_reserve_login_attempt` in `ui/auth_backends.py`); on another database it would need `select_for_update` or similar.

**Production-only behavior** (when `DEBUG=False`): `SECRET_KEY` is required, SSL redirect and secure cookies are on, and static files use whitenoise's `CompressedManifestStaticFilesStorage` (configured through `STORAGES`). Reference static files with `{% static %}` so they get hashed, long-cached names, and run `collectstatic` on every deploy. Also, `bluebook_project/middleware.py` adds a strict CSP. Any new external script, style, font or frame origin must be added to `CSP_POLICY` there, or it will work in dev and break in production.
